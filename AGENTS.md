# Overview

This file provides guidance for coding agents when working with code in this repository.

## Project Summary

Tip Genius is an AI-powered soccer match prediction system that combines Large Language Models (LLMs) with real-world odds data to generate informed predictions. The system features a modern Progressive Web App (PWA) frontend and a Python-based prediction engine that runs on Vercel's serverless platform.

## Smoke Tests

`tests/smoke/test_tip_genius_workflow.py` invokes every active provider via
`LLMManager.get_prediction()`. Gated by the `smoke` marker and `RUN_SMOKE=1`
(deselected by default). Each run costs real API spend — never execute
automatically. **Suggest running** after changes to `cfg/llm_config.yaml`,
`cfg/tip_genius_config.yaml`, or `lib/llm_manager.py`.

To check a single active provider — e.g. after changing its model id — narrow
the same test with `-k` instead of running the full sweep:

```bash
RUN_SMOKE=1 uv run pytest tests/smoke -m smoke -k Mistral-Ministral -v
```

A retired or renamed model surfaces here as a 404 from the provider.

The test parametrizes over `llm_provider_options`, so `-k` cannot reach a
commented-out provider — it selects zero tests and exits 0. Enable the provider
first, or call `LLMManager.get_prediction()` directly.

## Architecture Overview

### Frontend (`public/`, `api/`)

- `index.html` + `js/main.js`: the tips page (predictions per league from `api/predictions.js`)
- `dashboard.html` (served at `/dashboard`, rewrite in `vercel.json`) + `js/dashboard-data.js`: the statistics page. The data module loads the dashboard JSON from `api/stats.js` (on localhost from `samples/dashboard_stats.sample.json`, `?src=` overrides), applies the ranking and listing rules (rank by Avg, competition ranking for ties, models under 80 % of the best-covered model's matches or inactive are hidden, backfill switch, fair comparison) and keeps the filters in the URL (`season`, `league=pl|bl|ll|cl`, `all=1`, `backfill=0`, `fair=active|established`, `view=hits|recent`). Charts use Chart.js 4 from jsDelivr
- `js/models.js`: model names and logos for both pages (see Development Notes)
- Both pages share the header, the title block and the league bar: the tabs are static markup in each HTML file, so the bar is part of the first paint; the scripts only switch the state classes (`setActiveTab()` in `main.js`, `renderLeagueTabs` in `dashboard.html`). A change to the tab look goes into both HTML files. Switching pages cross-fades (`@view-transition` in `src/css/styles.css`), and the other page is prefetched on hover (speculation rules)
- Local preview of the statistics page: any static server on `public/` (the page then reads the sample JSON); regenerate the sample with `utils/backfill_stats.py --dry-run --save-dir`

### Key Python Modules

- `tip_genius.py`: Main workflow orchestrator and TipGenius class
- `lib/llm_manager.py`: Handles multiple LLM providers (Mistral, OpenAI, Google Gemini, etc.)
- `lib/api_data.py`: Fetches and processes odds data from external APIs
- `lib/storage_manager.py`: Manages data persistence to Vercel KV, the file system and the Vercel Blob archive
- `lib/blob_archive.py`: Blob archive pathnames, payloads, manifest/index helpers and `BlobArchiveReader`
- `lib/results_archive.py`: final match results (openligadb/ESPN, 90-minute scores, fuzzy team matching) and the Blob results CSVs; shared by the workflow, `utils/eval_providers.py` and `utils/backfill_results.py`
- `lib/team_matching.py`: Fuzzy matching for team logos and names
- `lib/prediction_table.py`: the Blob prediction table (`stats/predictions_<season>.csv`, one row per fixture and provider: pick rule, UEFA legs, odds, incremental watermark update with guards)
- `lib/stats.py`: model-comparison statistics (Kicktipp scoring, offered/missed semantics, matchdays, baselines, fair comparison, reliability) and the dashboard JSON; shared by the workflow and `utils/eval_providers.py`
- `lib/dashboard.py`: gathers the statistics inputs from Blob (updates the current table, reads the other tables and the results CSVs) for the workflow step and `utils/backfill_stats.py`

## Development Notes

- Always prefer standard Tailwind classes over arbitrary values (e.g. `w-56` not `w-[224px]`) — arbitrary values may be purged
- **Reasoning Model Support**: OpenRouter reasoning models (GPT-OSS 120b) use `reasoning.effort` parameter; Google Gemma uses native `thinkingConfig` with `thinkingLevel: minimal` option; NVIDIA Nemotron disables thinking via `chat_template_kwargs.enable_thinking: false` (with thinking on it was slow and often returned empty content); Google response parser skips thought parts to extract the actual answer
- **Code fence stripping**: `strip_code_fence` in `lib/llm_manager.py` unwraps fenced responses for every provider (some models wrap JSON in ` ```json ` even in JSON mode, which breaks the `literal_eval` in `tip_genius.py`). Unfenced responses pass through unchanged.
- **Provider keys select the request/response shape**: a key starting with `anthropic` uses the native Anthropic Messages format, `google` uses the Gemini format, everything else uses the OpenAI-compatible format. Name OpenRouter-hosted models `openrouter-*` regardless of who made the model, or the wrong parser is used.
- **Model names and logos** live in one list, `public/js/models.js` (`window.TIP_GENIUS_MODELS`), read by the main page's model picker (`main.js`) and the stats dashboard (`dashboard-data.js`); rename a model there only. **Retiring a frontend provider**: set its `offered` to `false` there (keep the entry so the dashboard still names its history); that is enough — `resolveLlmProvider` migrates users whose stored selection is gone.
- **Dead provider detection**: `_get_dead_providers` flags any provider with zero valid predictions and the workflow exits 1, after the export has been attempted. The report names the dead and healthy providers and points at the job log — it deliberately makes no claim about what reached storage, since the export can fail or partially fail. Partial failures and weeks without fixtures do not trigger it. A total odds API failure is reported separately by `_odds_api_unavailable`.
- **Odds snapshot logging**: `log_odds_snapshot` in `tip_genius.py` archives the bookmaker odds fed to the LLMs in Blob (see below) and also writes one `ODDS_SNAPSHOT {json}` INFO line per league and run as a cheap second copy. GitHub keeps Actions logs for 90 days only; the log line stays on purpose as a free fallback (`backfill_blob_archive.py` can recover odds from it if a Blob write fails).

## Vercel Blob Archive

Every non-debug workflow run archives its predictions and odds in the private Blob store `tip-genius-archive` as an additional, write-once copy. KV keys, values and timing are unchanged; KV stays the frontend's live store.

- **Token**: `BLOB_READ_WRITE_TOKEN` (name configured as `blob_token_env_name` in `cfg/vercel_config.yaml`, read by the `vercel` SDK). The GitHub secret is set in both environments (Production for the cron, Preview for manual `workflow_dispatch` runs), so manual runs are archived too; debug runs (`DEBUG_MODE=TRUE`) skip Blob in code. Switch: `export_to_blob` in `tip_genius.py`.
- **Layout** (flat, the leading timestamp sorts files chronologically):
  - `predictions/<YYYY-MM-DD_HH-MM-SS>_<base_key>.jsonl`: same timestamp and content as the timestamped KV key, one `{"name", "timestamp", "matches"}` line per league
  - `odds/<run_ts>_Match_Odds_<League-Key>.jsonl`: one file per league and run, `{"name", "timestamp", "columns", "matches"}` with columns `id, commence_time, home_team, away_team, odds_home, odds_draw, odds_away` (backfilled log-line odds have no `id`)
  - `odds/reconstructed/<ts>_Match_Odds_Reconstructed.csv`: ESTIMATED odds from `utils/reconstruct_odds.py`, never mixed into `odds/`; with several CSVs, the newest one (highest timestamp) is current
  - `predictions/backfill/<run_ts>_<base_key>.jsonl`: predictions generated AFTER the fact for a past run by `utils/backfill_llm_predictions.py` (late-joining providers); same lines as live files plus `"backfill": {"generated_at", "odds_source": "logged" | "reconstructed" | "mixed", "script"}`. Never treat them as pre-match predictions
  - `runs/<run_ts>.json`: manifest per run with the odds and prediction pathnames actually written
  - `results/<season>_<League-Key>.csv` (season as `2026-27`): final scores after **90 minutes** (Kicktipp scores regular time; extra-time games use ESPN period data checked against the final score), one row per predicted fixture, columns `match_key, league, season, kickoff_utc, home_team, away_team, home_goals, away_goals, status, source, source_id, source_home_team, source_away_team, match_score, fetched_at`. `match_key` = `<league name>|<kickoff UTC %Y-%m-%dT%H:%MZ>|<home_team>|<away_team>` in the prediction records' own spelling (`results_archive.prediction_match_key` builds it from any record), so joins need no fuzzy matching. A fixture predicted with a kickoff that later moved gets a copy of its pairing's row (domestic leagues only). Unmatched fixtures are only logged. Rewritten in place (cache 60 s); read with `blob_archive.read_fresh`
  - `stats/predictions_<season>.csv` (season as `2026-27`): the dashboard's prediction table, one row per fixture and provider (`lib/prediction_table.py`), columns `match_key, league, season, kickoff_utc, home_team, away_team, provider, tip_home, tip_away, predicted_at, origin, tip_kickoff_utc, live_runs, odds_home, odds_draw, odds_away, odds_at, odds_source`. Pick rule: the latest prediction made before kickoff (same as the old backtest); a rescheduled fixture is one row per provider with the kickoff of its newest record, UEFA repeat pairings more than 7 days apart stay separate legs. `match_key` joins the results CSVs. `origin` is `live` or `backfill`; `live_runs` lists the live runs that tipped the fixture before kickoff (per-run reliability). Odds: the latest odds file before kickoff (`odds_at` = its `run_ts`, `odds_source=logged`), else the reconstructed CSV (`reconstructed`). Regenerable from the archive; rewritten in place (cache 60 s), read with `blob_archive.read_fresh`
  - `index.json`: every run (newest last), the reconstructed files, under `backfill_predictions` (`{run_ts: {provider_key: pathname}}`, separate from `runs`) the backfill prediction files, under `results` (`{pathname: {rows, updated_at}}`) the results CSVs under `results_scan` (`{season: {through, files, digest, open, full_scan_at, updated_at}}`) the results step's scan state, under `stats` (`{pathname: {rows, updated_at}}`) the prediction tables and under `stats_scan` (`{season: {through, files, digest, odds_files, odds_digest, reconstructed, retry, full_scan_at, updated_at}}`) their scan state; overwritten like the results CSVs. `update_backfill_index` writes once per backfill run, refuses a read that lacks files seen earlier (fresh reads can lag behind a write) and reads back to verify, with bounded retries. The run's own update (`update_index` from `finalize_blob_archive`) has the same guards: it never overwrites a read that lacks files of the index read at the start of the run, and polls the read-back for the run entry, the carried entries and the scan states (up to 4 attempts); a failure is a WARNING naming `backfill_blob_archive.py --rebuild-index`. Read it with `BlobArchiveReader` instead of `list` (an advanced operation)
- **Join odds ↔ predictions** on `(home_team, away_team, kickoff)`; convert the predictions' `commence_time_str` (Europe/Berlin) to UTC first.
- **Run timestamp**: `run_ts` is set once per run (`StorageManager.run_ts`) for odds files, manifest and index entry; prediction files reuse their KV key timestamp.
- **Results step**: each non-debug run first calls `StorageManager.update_results_archive()` (before fetching odds). It runs incrementally (`results_archive.plan_scan`): it reads only the current season's prediction files with a `run_ts` after the `results_scan` watermark (`through`) plus the fixtures the state lists as `open` (not played yet, unmatched, or waiting for a rescheduled pairing's row), targets every one that kicked off over 3 h ago without a row, fetches only those days from openligadb/ESPN, and rewrites only the CSVs that gained rows (~4 puts plus one index update). It reads **all** of the season's prediction files instead (full scan, the repair path) when the state is missing or invalid, when the files at or before `through` no longer match the stored `files`/`digest` (a backfill file or late index entry for an old run), or when the last full scan is over 30 days old. The log line `Results archive: read N prediction files` shows the count. A fresh read with fewer rows than `index.json` lists is stale: retried, then skipped without writing. Every write is read back, polled after a settle pause (`blob_archive.READBACK_DELAYS`, ~45 s in all, before it puts again): an overwritten blob can serve its old content for 15 s and more even under its new etag (seen 10.11.2026, the log line `read-back current after N s` tracks it). The state advances once every prediction file was read; a stale CSV or an unverified write only keeps its fixtures `open`, so the next run re-checks just those (an unverified write that did land re-adds its index entry). It is written with the results index update and carried, with the verified `results` entries, into `finalize_blob_archive`'s index update, also when the step's own index update was not verified. `backfill_results.py --rebuild` drops the rebuilt seasons' state, so the next run scans fully. Never raises, never affects the exit code
- **Dashboard stats step**: right after the results step and before the odds fetch, each non-debug run calls `StorageManager.update_dashboard_stats()`: it brings the current season's prediction table up to date incrementally (reads only prediction and odds files with a `run_ts` after the `stats_scan` watermark and merges them into the existing rows; full scan of the season's prediction files when the state is missing or invalid, older files or the reconstructed CSV changed, the last full scan is over 30 days old, or the results step scanned fully in the same run; odds are carried over in a full scan and re-read only when the older odds files changed), reads the other seasons' tables and every results CSV, computes the statistics JSON (`lib/stats.py`, from Blob data only) and writes it to KV under `stats_kv_key` in `cfg/vercel_config.yaml` (`dashboard_stats`). It reuses the index, results CSVs and prediction files the results step already read. Guards as for the results CSVs: never shrink (row counts in `stats`), fresh reads, read-back verification; the table entry and state go into `finalize_blob_archive`'s index update (also in a run without new predictions); the state advances once the table is in Blob as computed, and files a run could not read are listed under `retry` and read again next run (no full scan). Without a state (before `utils/backfill_stats.py --execute`) the first run builds the current season's table itself (~275 simple operations in Nov 2026). A failure only logs a WARNING and the previous JSON stays in KV; never affects predictions or the exit code
- **Dashboard JSON** (`dashboard_stats`, served by `api/stats.js` at `/api/stats` for `/dashboard`, ~85 KB in Nov 2026, target < 100 KB, a WARNING above): `version`, `meta` (generated_at, data_through, counts, column lists, rules), `models` (ordered list; rows refer to models by index; `active`, `late_joiner`, `first_live`, `backfill`), `slices` keyed `<season>|<league>` with `all` (leaderboard, `live` rows without backfill tips, timeline, fair comparison on common fixtures, reliability) and `recent` (last 3 matchdays per league). Baselines `Odds-Favourite` (shown as "Favourite 2:1": the favourite wins 2:1, i.e. 2:1 home / 1:2 away favourite), `Always-2:1` and `Consensus` (median tip per side, .5 rounded up) appear everywhere. Each new season adds 6 slices (~25 KB): trim old seasons' per-league slices before the JSON outgrows the frontend budget
- **KV limits** (Upstash Redis free plan, upstash.com/pricing/redis, checked 09.11.2026; Vercel KV stores were moved to Upstash in Dec 2024): max request size 10 MB, max record size 100 MB, 500K commands per month, 250 MB data, 10 GB bandwidth per month. The stats step costs one `SET` per run; `api/stats.js` serves the JSON with a CDN cache of one hour (`s-maxage=3600`, `stale-while-revalidate` one day) and a browser cache of 5 minutes, so KV sees about one `GET` per hour and CDN region instead of one per dashboard load
- **Failures** only log a WARNING (pathname, HTTP status) after at most one retry and never affect the exit code or `export_results()`. Debug runs skip Blob with one INFO line.
- **Backfill**: `utils/backfill_blob_archive.py` skips files a live workflow run in `index.json` already archived (per-run window: 30 min before its `run_ts` to 4 h after) and attaches missing ones to that run, so failed live writes stay recoverable and nothing is archived twice. Re-run `utils/reconstruct_odds.py` before the backfill. Never run the backfill, `utils/backfill_llm_predictions.py --execute` or `--rebuild-index` near the cron (Tue/Fri 03:00 UTC): the index update is a read-modify-write.
- **Limits** (Hobby): 2,000 advanced operations (uploads, lists) and 10,000 simple operations (HEADs, cache-miss downloads) per month; a regular run needs ~12 uploads plus up to ~5 for the results step and 1 for the stats step (the prediction table, only when it changed; its index entry rides on the run's index update). Private blobs are downloaded through the API (simple operations, no CDN hits), so the results step reads only the new prediction files (~5–15 per run, plus a few HEADs and CSV reads); the monthly full scan reads the whole season once (~260 files in Nov, ~650 by May). The stats step shares those prediction reads and adds ~10–15 simple operations per run: the new odds files (~3–4), the current table (HEAD + GET, plus HEAD + GET for the read-back), the past season's table and results CSVs (plain GETs, ~5) and any current results CSV the results step did not read; its monthly full scan coincides with the results step's and re-reads no odds. `utils/backfill_stats.py` reads every prediction and odds file of 2025/26 and 2026/27 once (~920 simple operations in Nov 2026, cached on disk for re-runs) plus 2 puts and one index update.
